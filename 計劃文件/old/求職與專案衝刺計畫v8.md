## Phase 1：專案任務清單

| 任務 | 核心實作內容 | 完成定義 | 學習與說故事亮點（面試用） |
|---|---|---|---|
| **1 骨架與路由** | Vite 建立、裝 Router、資料夾結構、路由設定 | 能在各步驟路由間跳轉、畫面空白但不報錯、無任何 `.ts` 檔 | 建立單頁式應用（SPA）基礎路由結構 |
| **2 Step1基本資料<br>(Local 版)** | 暫用 `ref` 存資料。**不寫 `v-model`**，改用 `:value` 搭配 `@input` 手寫雙向綁定底層，並用原生 JS Regex 驗證。 | Step1 可獨立操作、Regex 能擋下錯誤格式。 | 深入理解 Vue 響應式核心與 `v-model` 語法糖原理。 |
| **3 Step2條件式欄位<br>(Local 版)** | 依身份別正確顯示欄位。**此時會觸發痛點**：當切換路由至 Step 2 再切回 Step 1 時，發現資料因元件卸載（unmount）而全部遺失。 | 條件式欄位能正常切換與顯示。 | **觸發痛點**：親身體會跨路由切換導致 Local State 遺失的開發痛點。 |
| **4 Pinia 救援引入** | **正式引入 Pinia + Persist**。設計全域 Store，將 Step 1 & 2 的 Local 資料重構收歸全域 Store。 | Store 可正確存取，Reload 網頁後資料依然存在。 | **技術決策**：能清晰說明為什麼要在這個時機點引入全域狀態管理。 |
| **5 驗證重構<br>(VeeValidate+Zod)** | 將手寫驗證重構為 VeeValidate + Zod schema（含 Step 2 的條件式 schema 判斷）。 | 表單功能正常，程式碼更簡潔優雅。 | **架構演進**：說明從「手寫 Regex」過渡到「宣告式 Schema 驗證」的維護性差異。 |
| **6 Step3 帳號設定** | 密碼規則、Zod `.refine()` 兩次密碼相符判斷、自訂 async 帳號檢查 + debounce。 | 完整走完前三步不出錯，異步檢查不狂發 API。 | 掌握非同步流程、Promise、以及 Debounce 優化效能的原理。 |
| **7 Step4 與送出** | 確認頁、讀取 Store 唯讀資料、`try/catch` 串接模擬 API 與 HTTP 狀態碼分流。 | 完整流程不 crash，依狀態碼（200/401/500）顯示對應 UI。 | 掌握 API 錯誤處理與使用者體驗優化。 |
| **8 後台管理** | AdminList 表格篩選、AdminDetail (彈窗複用元件)、簡易路由守衛（Guard）。 | 未登入會被擋在 `/admin` 外，後台可查看與刪除。 | 實作路由守衛與後台元件複用設計。 |
| **9 收尾與部署** | UI 打磨、404 頁面、README（含設計決策與已知限制）、部署上線。 | 有分享連結、有 Git 階段性 commit 紀錄。 | 完整的專案工程化收尾與部署經驗。 |
| **10（可選）** | User Login ＋ 我的報名紀錄。 | 視時程決定做不做。 | 增加系統完整度。 |

### 任務結束固定儀式：STAR 反思記錄
每完成一項任務，請錄音 5 分鐘，並用 **STAR 原則** 寫下以下 4 題回答：
1. **【Situation / Task 痛點與挑戰】**：這個任務中，我遇到了什麼技術難關或開發痛點？
2. **【Action 解決行動】**：我嘗試了哪些方法？最後為什麼選擇這個 A 方案？（例如：為什麼選擇 Pinia 而非繼續用 Local State？）
3. **【Result 成效驗證】**：解決後的程式碼品質或使用者體驗提升了多少？
4. **【Reflection 技術反思】**：學到了什麼新觀念？如果能重寫一次，我會怎麼改？
