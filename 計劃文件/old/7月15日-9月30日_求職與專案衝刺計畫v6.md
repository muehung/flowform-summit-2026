# 7/15 – 9/30 求職 + 專案衝刺計畫（FlowForm Summit 2026）

> 專案名稱：**FlowForm Summit 2026**（履歷/作品集顯示用）；GitHub repo建議命名 `flowform-summit-2026`。
> 基礎：附件3《多步驟報名表單練習計畫_純JS版》，原為6天衝刺版，此處展開為約2週的紮實版本，並接上求職期。
> 前提：目前無兼職，每天可投入 6 小時以上；策略為「先衝刺專案，再全力求職」。
> 情境：iT研討會報名系統。
> 版本紀錄：
> - v1：拉長為2週+接上求職期
> - v2：採納ChatGPT建議，加入 Phase 0 需求釐清、JS暖身跟著任務走、Admin拆成獨立一天、每日錄音與反思
> - v3（本版）：依 NotebookLM 對照《JS 60天計畫》的落差分析，補上原生DOM操作、進階陣列方法、API錯誤處理、開源專案閱讀、知識系統化五個項目

## Phase 0：需求釐清（7/15 上午，2-3小時，寫Day1之前）

**不要一開始就 `npm create` 然後直接寫。** 很多人第一天建專案、第三天全部重拆，就是因為需求沒想清楚。花2-3小時把下面這些定案：

- [ ] 有哪些頁面？（Step1~4、Success、AdminList、AdminDetail）
- [ ] 每頁有哪些欄位？
- [ ] 每個欄位的驗證規則是什麼？
- [ ] Pinia store 要放什麼資料？結構長怎樣？
- [ ] Component 怎麼拆？（哪些是共用的，例如進度條、確認彈窗）
- [ ] 畫一張流程圖，例如：
  ```
  App
   └→ Step1 → Step2 → Step3 → Confirm → Success
  ```
  可以手繪拍照，或用 Excalidraw / FigJam，不用精美，重點是想清楚。

**這一步做完，後面Day1~Day6的速度會明顯變快**，因為架構跟資料形狀都已經定案，不會邊寫邊改。

## Phase 1：專案衝刺（7/15 起，抓約2週，但**不卡日期，卡任務**）

**結構調整說明**：原本這裡是「日期對應學習主題+任務」的表格，但這種結構會製造「今天沒做完=落後」的心理壓力，跟實際開發節奏不合——有的元件本來就比較花時間（就像Phase0）。改成**任務清單**，照順序做完一項才往下一項，不設每個任務的時間期限。

**JS概念是「可能用到」，不是「規定要用」**：每個任務底下列的JS概念（例如map、filter），意思是「做這件事很可能自然會用到」，不是「這裡一定要刻意套用這個方法」。同一個目標常常有不只一種寫法可以達到——例如「把狀態碼轉成顯示文字」，用`map`可以做到，用一般的`for`迴圈也能得到完全一樣的結果，差別只在寫法風格，不是誰對誰錯。目標是「功能做出來、你看得懂自己寫的東西」，不是「有沒有用到某個特定方法」，看到清單上列的方法覺得卡住，直接跳過用自己順手的寫法就好。

**任務清單全部完成後，先完整休一週，再進入Phase2**：不是拿來趕工用的緩衝天，是真正的休息，不排任何任務。原本分散在週末的零碎緩衝改成這樣集中的一整週，因為2天2天分散著留，感覺上等於沒留，不如集中起來確保真的有恢復到。

### 任務1｜專案骨架 + 路由設定
- Vite建立專案（JS模板）、安裝pinia/persist/vee-validate/zod/vue-router
- 資料夾結構、路由設定（`/register/step-1`~`step-4`、`/register/success`、`/admin`）
- **完成定義**：能在路由間跳轉、畫面空白但不報錯、無任何`.ts`檔案

### 任務2｜Pinia Store + useStepForm composable
- 設計store資料結構（currentStep/formData/submissions）、寫actions（nextStep/prevStep/resetForm等）
- 接上persist，測試reload後資料還在
- **完成定義**：store可正確存取並持久化，手動測過3-5種情境
- 可能用到：Object spread、解構、reference vs value

### 任務3｜Step1 基本資料元件
- **先手寫**一版驗證邏輯（原生JS：regex檢查email/電話，可嘗試不用v-model、改用`querySelector`+`addEventListener('input')`+`classList`練習原生DOM操作）
- **再重構**成Zod schema + VeeValidate接入
- **完成定義**：Step1可獨立操作、驗證正確、資料寫入store
- 可能用到：String方法/replace/match/test/regex

### 任務4｜Step2 條件式欄位元件
- **先手寫**條件式判斷邏輯（依身份別決定必填欄位，同樣可嘗試原生DOM操作）
- **再重構**成條件式zod schema（discriminatedUnion或依identity動態決定必填欄位）+ 動態欄位渲染
- 欄位讀取練習用`?.`防止資料不存在報錯，選填欄位（如部門）用`??`給預設值
- **完成定義**：Step2可獨立操作、依身份別正確顯示欄位、驗證正確

### 任務5｜Step3 帳號設定元件
- **先手寫**密碼規則+兩次密碼相符判斷（可嘗試原生DOM操作）
- **再重構**成zod `.refine()` + `useAsyncUsernameCheck` composable（模擬API延遲800ms）+ debounce
- **完成定義**：完整4步驟走一次不出錯，async帳號檢查正常運作
- 可能用到：Promise、async/await、setTimeout、debounce原理

### 任務6｜Step4 確認頁 + 完整流程串接
- 唯讀顯示store資料、提供「上一步修改」按鈕
- 送出邏輯：`submitRegistration`→寫入`submissions`→`resetForm`→導向`/register/success`
- 加入`try/catch`，依模擬狀態碼（200/401/404/500）分別顯示對應UI訊息（inline，不做獨立500頁面）
- **完成定義**：完整報名流程無bug走完一次，錯誤狀態有對應處理
- 可能用到：淺拷貝/深拷貝、資料流整體回顧

### 任務7｜後台管理（AdminList + AdminDetail）
- AdminList：表格、篩選（身份別/關鍵字）
- AdminDetail：**採用彈窗**，複用Step4的摘要顯示component；刪除功能（二次確認）
- Admin Login：demo版簡易路由守衛（檢查是否已登入管理員才能進入`/admin`）
- **完成定義**：後台可完整操作（查看/篩選/刪除），權限守衛能擋住未登入訪問
- 可能用到：forEach/map/filter/some/every/includes

### 任務8｜收尾：打磨 + 上線
- UI細節打磨、loading狀態、錯誤訊息樣式、404錯誤頁（Router catch-all + 靜態元件）
- 寫README（含設計決策、已知限制）
- 部署（Vercel/Netlify）+ push GitHub（分階段commit）
- **完成定義**：有可分享連結、GitHub repo有階段性commit紀錄

### （可選，時程緊可捨棄）任務9｜User Login + 我的報名紀錄
- 沿用Step3已建立的帳號資料，前端本地比對即可
- 忘記密碼頁僅做UI展示，不接真實寄信

---

**完成一個任務後的固定儀式**（不用每天做，做完一個任務就做一次）：
1. **5分鐘口頭錄音**：講「這個任務做了什麼、為什麼這樣做、哪裡卡住」
2. **4題反思（3分鐘寫下來）**：
   - 這個任務最大的收穫？
   - 最大的Bug？
   - 學到的新JS？
   - 如果重寫一次，我會改什麼？

這些記錄會累積成之後寫README跟準備面試故事的素材，不用擔心進度快慢，累積下來的品質才是重點。

專案完工後，把它變成求職武器，同時盤點求職準備。同樣不綁固定日期，照順序做完即可。

| 順序 | 內容 |
|---|---|
| 1 | 更新104自我介紹段落（加入FlowForm Summit 2026連結與一句話技術亮點）+ 更新作品集PPT加入新專案 |
| 2 | 面試話術整理：針對 Composition API、Pinia store 拆分、VeeValidate+Zod分工，各準備2-3個問答草稿；同步整理一份「個人技術筆記」：把專案中用到的JS重點（Promise原理、解構賦值、Regex、原生DOM操作 vs Vue雙向綁定的差異）整理成語法速查表，這份筆記本身也是履歷/作品集的加分素材 |
| （休息） | 可視狀態安排1-2天緩衝：複習雇主評估框架checklist、回顧過去模擬面試回饋 |

## Phase 3：求職全力衝刺（Phase2完成後開始，約8週）

每週固定節奏，8週皆可套用，第一週先建立習慣。這裡的「週」是指開始求職衝刺之後的第N週，實際對應到哪個月曆日期，看Phase1、Phase2實際花了多久。

### 每週節奏模板
- **投遞**：每週目標投遞 10-15 家（可依回覆率調整）
- **面試準備**：當週有面試 → 優先準備該公司資料、模擬問答；無面試 → 持續精進自我介紹與專案講解流暢度
- **技術維持**（每週2-3次，每次1小時內即可）：
  - 複習重點可對照附件1《JavaScript 60天學習計畫》中 map/filter/find、async/await、fetch/AJAX 相關段落做「重點複習」而非整輪重跑
  - 延續Phase1的口頭練習習慣：練習講解自己專案裡的技術決策
  - **開源專案拆解任務**：每2週安排一次，挑一個簡單的Vue3開源專案，練習找出頁面入口、API service封裝位置、共用元件怎麼被使用，寫一篇「閱讀筆記」（格式可沿用附件1的頁面閱讀筆記模板）。這是補回《60天計畫》Day43-60「閱讀既有專案」的實戰經驗——FlowForm Summit 2026是從0到1新建，跟「維護別人寫的舊程式碼」是不同的能力，求職後大機率會遇到後者
- **每週檢視**：上週投遞數、回覆率、面試場次、被拒或已讀不回的原因初步判斷，微調履歷/求職信

### 8週分配建議

| 週次 | 重點 |
|---|---|
| 第1週 | 密集投遞起步，建立節奏；第一輪面試邀約若出現，優先準備 |
| 第2週 | 持續投遞；依第1週回饋微調履歷/自我介紹；**開源專案拆解任務#1** |
| 第3週 | 持續投遞+面試；技術維持聚焦Vue3生態（Router/Pinia原理問答） |
| 第4週 | **期中檢視**：整體回覆率、面試表現，必要時調整求職策略或投遞產業範圍；**開源專案拆解任務#2** |
| 第5週 | 持續投遞+面試；若已有多輪面試，開始準備薪資談判/offer比較材料 |
| 第6週 | 持續投遞+面試；**開源專案拆解任務#3** |
| 第7週 | 持續投遞+面試；技術維持聚焦被問過但答得不夠好的主題 |
| 第8週 | **收尾檢視**：盤點整體求職狀況，若尚未定案，規劃後續策略；**開源專案拆解任務#4** |

## 提醒

- Phase 0 花的時間看似「還沒開始寫code」，但能省下後面重拆架構的時間，是划算的投資，花比預估久也不用焦慮。
- Phase 1 改成任務清單制，就是為了拿掉「今天沒做完=落後」的壓力——裸辭後的復原期需要更彈性的節奏，不是用日期逼自己。
- Admin頁面跟收尾任務分開，是為了避免最後階段塞太多任務、Bug一直修到README跟部署都沒做完。
- 手寫驗證改用原生DOM操作，是刻意的：Vue開發久了容易忘記`v-model`底層到底做了什麼，面試被問「Vue雙向綁定原理」時，有實際手寫過DOM事件的經驗會答得更扎實。
- 清單上列的JS方法（map/filter等）是「可能用到」的參考，不是規定；同一個目標常常不只一種寫法能達成，用自己看得懂、順手的寫法就好。
- 開源專案拆解任務是為了補「維護舊專案」的能力——這跟「自己從0到1做專案」是不同的肌肉，求職進去後幾乎一定會遇到前者。
- Phase 3 的技術維持不是重新學，是「保持手感」，時間抓短即可，避免排擠投遞與面試準備時間。
- Phase1任務清單全部完成後，先完整休一週再進Phase2，這是真正的休息，不是拿來趕工的緩衝。
