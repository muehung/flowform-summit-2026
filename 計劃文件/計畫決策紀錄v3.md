# 計畫決策紀錄

> 記錄FlowForm Summit 2026專案 + 求職計畫在調整過程中，如何權衡以下三個核心考量。

---

## 三個核心考量

1. **javascript-60-day-learning-plan-byLucus.md**（前輩規劃）
   代表「JS基礎要紮實」的完整學習藍圖，涵蓋基礎語法→DOM/事件→資料處理→非同步→API→讀專案→實戰修改，共60天、8週的完整訓練節奏。

2. **面試demo專案**（FlowForm Summit 2026）
   代表「要有東西可以講、可以展示」的具體產出，核心賣點鎖定在Vue3 Composition API、Pinia、VeeValidate+Zod條件式驗證這三項技術亮點，範圍刻意收斂、不做真後端。

3. **短時間**
   代表現實限制：裸辭後要儘快求職，不能無限期學習準備，時間分配上求職本身也要佔位置。

---

## 核心張力

- 60天計畫如果照表操課，等於「先花2個月學JS，才開始做專案、才開始投履歷」——跟「短時間」直接衝突。
- 面試demo專案如果照單全收所有外部建議（ChatGPT/Grok/NotebookLM的建議都陸續加進來），範圍會不斷膨脹，排擠掉打磨核心三項技術亮點的時間——這也跟「短時間」衝突。
- 但如果為了省時間，完全略過60天計畫、也不接受任何外部建議，又會讓demo專案的JS基本功不夠扎實，面試被問細節會答不出來——這跟「面試demo專案」的存在意義衝突。

## 最終處理原則

**不做加法，做置換。** 三個考量不是三條平行的待辦清單相加，而是：

1. 以「面試demo專案」的11個工作天排程為主骨架，時間不延長。
2. 把「60天計畫」拿來當**稽核清單**，逐一核對哪些主題已經被demo專案的開發過程自然覆蓋（例如：寫Pinia store會用到Object操作、寫Step3驗證會用到async/await），只有**真正沒被覆蓋到的落差**才額外處理（最終只剩：`?.`/`??`、權限判斷role/canView兩項，且都塞進既有天數，沒有加時間）。
3. 對外部建議（ChatGPT、Grok、NotebookLM）採**先評估再採納**，不是照單全收：
   - 採納：對demo專案的技術深度或JS基本功有直接幫助、且能塞進既有時間的（例如「先手寫驗證再重構Zod」「Admin拆一天」「每日錄音反思」）
   - 分級處理：對demo有加分但會增加範圍的（例如Grok建議的登入頁/我的報名紀錄），標記為「可選、放進緩衝日、時程緊可捨棄」，不擠壓核心工作日
   - 不採納或降低優先：對demo沒有實質加分、且需要額外基礎建設的（例如忘記密碼頁的真實寄信功能）
4. 「讀懂別人既有專案」這個60天計畫後段的核心能力（Day43-60），demo專案本身無法練到（因為是從0到1新建，不是維護舊code），改放進求職期（Phase 3）的雙週開源專案拆解任務，用不同的時間軌道處理，不硬塞進專案衝刺期。

## 一句話總結

> 60天計畫負責「檢查有沒有漏」，demo專案負責「決定範圍長什麼樣」，短時間負責「否決任何會拖時程的加法」——三者的優先順序是：**時間 > 專案範圍聚焦 > 學習完整度**，但學習完整度不會被完全犧牲，而是換成更省時的方式（稽核＋見縫插針）被保留下來。

## 套用案例：404頁、500頁要不要加？

用來示範這套判斷框架實際怎麼運作，之後遇到新的「要不要加OOO」的問題，都可以照這個順序問。

**問題**：Grok建議補404、500兩個錯誤頁面，都要加嗎？

**判斷步驟**：
1. 對demo專案的三個技術亮點（Composition API / Pinia / VeeValidate+Zod）有沒有直接幫助？→ 兩者都沒有，純粹是路由/UI層級的東西，不涉及核心技術亮點
2. 能不能塞進既有天數，不拉長時程？→ 404可以（Router catch-all + 靜態元件，15-30分鐘），500則要看有沒有重複已展示過的能力
3. 是否已經有其他地方展示過同樣的能力？→ 500這種「錯誤狀態處理」的能力，7/27的`try/catch`+狀態碼分流（inline錯誤訊息）已經展示過了，獨立做一個500頁面等於重複證明同一件事

**結論**：
- 404 → **加**，塞進7/29收尾日的UI打磨項目，理由是部署後外部連結亂點會出現空白頁，屬於「不加會扣分、加了成本很低」的項目
- 500獨立頁面 → **不加**，理由是核心能力（錯誤狀態處理）已經在7/27用inline訊息展示過，重複做只是花時間、不會讓面試官多看到什麼

**這個案例示範的判斷順序**：先問「對核心亮點有沒有幫助」，再問「成本能不能塞進既有時間」，最後多一步「有沒有跟其他地方重複展示同一件事」——第三步是這次新補上的判斷角度，之後遇到類似「要不要多做一個頁面/功能」的問題，都可以先檢查是否已經在別處證明過同樣的能力。

## 套用案例：男友提出的結構性質疑

這次不是「要不要加某個功能」的小判斷，而是對整個計畫**結構**的質疑，處理方式不太一樣，記錄下來避免以後又繞回舊結構。

**男友提出的四點**：
1. 時間安排不該從「要學什麼」開始，該從「元件」開始
2. 用學習方法（JS技巧）當task項目很怪，方法是達成目的的手段，不是目的本身——例如array不一定要用`.map`，用`for`迴圈也能達到同樣結果
3. 緩衝該留一整週，分散在週末的2天2天等於沒留
4. （後續延伸）如果3個月投入跟demo成果不成正比，該不該增加功能或換有趣主題

**處理結果**：
1、2、3點**直接採納**，因為指出的是計畫結構本身的問題，不是單一任務的取捨：
- 把Phase1從「日期表格」改成「任務清單」，做完一項才走下一項，不綁月曆日期
- 清單上列的JS方法從「規定」改成「可能用到的參考」，明確寫出「同一個目標常有不只一種寫法，用自己順手的就好」
- 緩衝從分散的2個週末，改成任務清單全部完成後**集中休一整週**，真正休息、不趕工
- Phase2、Phase3也跟著從固定日期改成相對順序/週次，避免跟已經不綁日期的Phase1兜不起來

第4點（增加功能 vs 換有趣主題）**沒有直接採納**，原因記錄如下：
- 先釐清「3個月」跟「花在這個專案上的時間」不是同一件事——3個月是整個求職週期，實際做這個表單專案大概只佔2-3週，不該用整個求職週期的長度去除以單一個專案的產出
- 「增加功能」風險：容易重新掉回範圍蔓延，跟先前「不做加法，做置換」的原則衝突，會排擠核心三項技術亮點的打磨時間
- 「換有趣主題」風險：Phase0已經把資料結構、頁面關係定案，換題目等於歸零重來，而且「有趣」不保證面試官買單——面試官通常更在意能不能講清楚設計決策，而不是題目表面吸引力
- 這一點目前處理方式是**先釐清問題本質**（怕面試官覺得不夠看？還是自己對題目沒動力？），沒有立即改動計畫，等使用者回答後再決定要不要調整

**這個案例的啟示**：外部建議（不管是ChatGPT/Grok/NotebookLM還是男友）分兩種，一種是指出**結構性問題**（例如日期綁死造成的壓力），這種通常值得直接採納，因為修正一次就能持續受益；另一種是**單點建議**（例如換主題、加功能），這種要先套用既有判斷框架（對核心亮點有沒有幫助/能不能塞進既有時間/有沒有重複展示），不要因為建議來自親近的人就跳過評估直接照做。

## 套用案例：ROI信心疑慮——有沒有證據？

**問題**：使用者擔心「多步驟表單題目太單薄、面試官不會欣賞」，導致沒信心投入，要求查核先前「junior前端常被考這類題目」的說法是否有依據，而不是安慰性斷言。

**查核方式**：實際web搜尋業界面試準備文章與資源，而非憑印象保證。

**查核結果**：
- 找到2025年整理前端機測常見題的文章，明確把「Multi-Step Form Wizard」列為常見題目，並說明測的是跨步驟狀態保存、驗證邏輯、受控元件，是junior/senior分水嶺
- 找到GitHub整理的面試準備清單，把「手刻多步驟表單＋驗證＋localStorage持久化」列為明確練習項目，與這個專案的Pinia persist本質相同
- 找到前端系統設計面試指南，強調面試官重視「為什麼」的設計取捨說明，而非功能多寡

**誠實揭露證據限制**：這些是業界從業者共識的整理文章，不是嚴謹學術研究或公司內部招募數據，不能保證任何一場面試都會被欣賞。準確說法是「這個題目落在業界公認junior前端常考、能看出深淺的範圍內」，不是「保證面試官會滿意」。

**啟示**：使用者要的是「證據」而不是「安慰」，這兩者不一樣——後續遇到類似信心疑慮，應優先查核有沒有可驗證的外部依據，並誠實區分「業界共識」與「保證結果」，不用模糊的保證話術取代查證。

## 套用案例：Gemini v9重構＋Tech Lead審查

**背景**：使用者請Gemini審查v8計畫，Gemini產出v9，核心變化是把「先規劃Pinia結構」改成「先寫Local State→親身體驗跨路由資料遺失痛點→才引入Pinia」的敘事驅動式重構，並加入MSW模擬真實API、STAR反思法、debounce放watcher而非Zod等設計。使用者請Claude以「資深前端Tech Lead」角色嚴格審查後更新為v10。

**審查結論（採納為主，3點修正）**：
- 整體方向**採納**：痛點驅動敘事技術上站得住腳（Vue Router預設會在路由切換時卸載元件、銷毀本地state，這個痛點是真的，不是硬湊教學情境），而且是把既有三個核心亮點做深，不是新增範圍，符合先前建立的ROI判斷原則
- 修正1：套件安裝時機要跟著敘事走——不能Task1就把pinia/vee-validate/zod全裝好，故事會矛盾（藥先準備好了才生病），改成用到哪個套件、哪個任務才裝
- 修正2：MSW是新工具、有學習曲線、不在原本三個核心亮點內，加一條「卡住可退回`setTimeout`模擬版，不影響檢核點」的安全網，避免它變成新的進度風險
- 修正3：v9的Task2用`:value`+`@input`是Vue響應式系統內的手寫雙向綁定，能講v-model原理，但跟NotebookLM抓到的「原生DOM querySelector/addEventListener/classList」缺口不是同一件事，加一個**選做**的原生DOM小段落，不強制、不佔用進度

**啟示**：這次的外部建議來源換成另一個AI（Gemini）而非人類（ChatGPT/Grok/男友），處理方式沒有不同——一樣先問「技術上站不站得住腳」「對核心亮點是深化還是新增範圍」「有沒有製造新的進度風險」，不因為建議來源是誰而放寬或收緊審查標準。
